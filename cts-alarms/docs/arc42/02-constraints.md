# 2. Architecture Constraints

Part of the [arc42 documentation](../README.md).
Previous: [1. Introduction and Goals](01-introduction-and-goals.md) · Next: [3. Context and Scope](03-context-and-scope.md)

Constraints are conditions the architecture has to live with. They are split into technical, organisational, and conventions. Each row names its evidence. Line references are to `main.py` v2.1.0.

## 2.1 Technical constraints

| # | Constraint | Consequence | Evidence |
|---|------------|-------------|----------|
| T1 | **The alarm source is a file on the CTS server.** TAC Vista 5.1.9 exposes its live alarm list only as `C:\ProgramData\Schneider Electric\TAC Vista 5.1.9\DB\$thisdb\$this.alr`, rewritten in place; there is no API or event hook the bot uses. | Anything that reads alarms must run on (or have file access to) the CTS server. Polling is the only option; the poll interval bounds how fast changes are seen and short-lived transitions between polls can be missed (the code explicitly handles "missed between polls", `main.py:1283-1287`). | `config.json` → `paths.vista_alarm_file`; `snapshot_alarm_file()` `main.py:205` |
| T2 | **File format is fixed by Vista:** tab-delimited, ISO-8859-1, 36 fields, no header, hex epochs, Danish alarm texts (line endings: CRLF on the server per the build reference, LF in the committed snapshot; the parser strips both, `main.py:223`). | Parser works by positional index; encoding must stay `iso-8859-1` (`config.json` → `log_encoding`); Danish characters (æ, ø, å) are in the data. | `main.py:120-133`, [ALR format](../reference/alr-file-format.md) |
| T3 | **Host: Windows Server 2016**, 32-bit Python 3.13 installed per-user at `C:\Users\GPST\AppData\Local\Programs\Python\Python313-32\python.exe`. | No containers, no services daemon; scheduling via Windows Task Scheduler; paths are Windows paths; `os.replace()` used for atomic renames on NTFS. | `TACVista_Alarm_Bot.xml` `<Command>`; `main.py:47` `DEFAULT_CONFIG_PATH = r"C:\priorityalarmsapi\config.json"` |
| T4 | **Scheduling: Windows Task Scheduler**, task `\TACVistaLogs\TACVista_Alarm_Bot`, every 5 minutes (`PT5M`) for 1 day repeating, start boundary 2026-04-21, execution limit 5 min, `MultipleInstancesPolicy=IgnoreNew`, `RestartOnFailure` 3× at 1-minute intervals, runs as user `GPST`, `LeastPrivilege`. | One run must complete within 5 minutes; overlapping runs are dropped, not queued; each run is a fresh process — what must survive a run is on disk: state files, the MainManager token cache (`mm_token.json`, v2.0.0+) and the shipper outbox. The shipper's `time_budget_seconds` (120) keeps a backlog resend inside the 5-minute limit. | `TACVista_Alarm_Bot.xml` |
| T5 | **MainManager REST API** at `https://rambollfm.mainmanager.dk`, changed by EG **without notice**: `/restapi/Incident/*` was removed on 2026-09-19; the bot now uses `POST/GET/PUT /api/v3/incidents` and the unchanged `POST /restapi/token` password grant. The v3 write model has no `Description`: `Remarks` is written as the full text but reads back truncated to ~245 characters, so `Description` must be read. | To add a line the bot GETs, prepends to `Description`, PUTs `Remarks` with the whole write model echoed, and GETs again to verify (`prepend_description_line()` `main.py:807`) — three round-trips per line. An unannounced API change can recur; the 404 classification limits the damage to one ERROR per run. | `MMClient` `main.py:624`, [ADR-0019](../adr/0019-mainmanager-v3-incident-api.md), [MainManager API](../reference/mainmanager-api.md) |
| T6 | **MainManager incident classification is fixed by the FM side:** `IncidentTypeID 277` ("CTS API"), `GradeID 10`, `StatusID 5`, `LocationID 6`, `ReportedByID 748` / `ReportedByOrganisationID 11`, and `MainID` = the object the incident belongs to (fallback `14228`). | Values are configuration, not code; `MainID` per alarm object must be maintained in `objects.csv` (currently empty). | `config.json` → `mainmanager.incident_defaults`, `default_main_id` |
| T7 | **Only one external Python dependency (`requests`)**; no packaging, no virtual environment on the CTS server (dependencies unpinned, [TODO T-029](../TODO.md)). | Deployment is "copy `main.py` (+ `shipper.py`) and `config.json`, create `secrets.json`"; changes are verified with the test suite on a developer machine and with `--dry-run` (read-only) on the server. | `main.py:33`; `tests/` |
| T8 | **Outbound HTTPS from the CTS server** to MainManager (proven) and to `api.digibuild.dk` (to be proven by the dry-run reachability line, [TODO T-077](../TODO.md)); no inbound access to the CTS server is assumed. | The CTS server pushes; nothing pulls from it ([ADR-0016](../adr/0016-cts-server-vs-vps-responsibility-split.md), [ADR-0020](../adr/0020-hmac-ingest-to-digibuild.md)). | outbound `requests` only; no listening socket in `main.py` or `shipper.py` |
| T9 | **Runtime data stays on the CTS server** (state JSON, snapshot, `csv/`, `logs/`); it is git-ignored. The copy of 2026-09-28 that was committed for the migration is archived privately on the VPS. | The repo is small again; historical analysis happens in digibuild. | [ADR-0022](../adr/0022-cts-side-only-repo-web-app-in-digibuild.md) |
| T10 | **HMAC ingest needs a correct clock:** the receiver rejects requests whose `X-Timestamp` is more than 300 s from its own clock. | The CTS server must be NTP-synchronised ([TODO T-107](../TODO.md)); a drift shows as `HTTP 401 … clock …` and batches queue in the outbox. | `shipper.py` `signed_headers()`; digibuild ADR-0022 |

## 2.2 Organisational constraints

| # | Constraint | Consequence | Evidence |
|---|------------|-------------|----------|
| O1 | **Single owner/developer/operator** (Georgi), building and running this next to other work; no dedicated ops team. | Simplicity and low maintenance weigh more than elegance; documentation must be self-sufficient. | Repo has one commit ("Initial commit"), one author; scheduler runs as the owner's Windows user. |
| O2 | **The BMS and Vista are operated by ISS/FM staff (the owner is one of the acknowledging operators, `GPST (Georgi ISS)` — the most frequent one in the data).** Operators acknowledge alarms in Vista; FM staff close tickets in MainManager. | The bot must be read-only towards Vista and must never close tickets ([ADR-0010](../adr/0010-prepend-description-never-change-status.md)). | Operator names in `$this.alr` field 10; `Alarm_bot_build_reference.md` §1 "operators close tickets manually"; `main.py:1274-1277` comment |
| O3 | **MainManager is a third-party SaaS (Ramboll FM)**; its API, IDs (`CheckwordID`, `GradeID`, `MainID`) and account are administered elsewhere. | The bot cannot create its own reference data; ID changes must be reflected in `config.json`/`objects.csv`. | `config.json` → `mainmanager` |
| O4 | **A sibling "Indeklima bot" exists** (temperature logs → MainManager, type 281, office hours), same author, **same MainManager account**, on the CTS server, not in this repo. | It broke with the same API removal and needs the same v3 port and the rotated password ([TODO T-105](../TODO.md)); its stale copy on GitHub (`slimyloki/vista-opc`) must not be changed or copied from. | `main.py:4-5` docstring; `Alarm_bot_build_reference.md` §15 |
| O5 | **The GitHub repository is public.** Its history holds the MainManager password of v1.x (rotated 2026-09-29) and runtime data with operator names. | Nothing secret or personal may be committed again (`.gitignore`, `tests/test_repo_hygiene.py`); docs name secrets by location only and carry no VPS addresses, ports or paths. Making the repo private / purging history is [TODO T-102](../TODO.md). | [ADR-0021](../adr/0021-secrets-in-secrets-json.md), [ADR-0022](../adr/0022-cts-side-only-repo-web-app-in-digibuild.md) |
| O6 | **The owner's standing hosting rule for new web apps:** pages and on-demand APIs on Vercel, only background processes on the VPS, Clerk login, Danish and English, one portal (digibuild) with sub-apps. | The web side of this system is a digibuild sub-project, not a server in this repo. | [ADR-0022](../adr/0022-cts-side-only-repo-web-app-in-digibuild.md) |
| O8 | **Deployment to the CTS server is the owner's hands.** Nothing on the VPS reaches into the building network. | Every change ships as files + exact steps; verification by `--dry-run` and the log. | [arc42 §7](07-deployment-view.md) |
| O7 | **Personal data is present in the data files** — operator names such as `GPST (Georgi ISS)` (the owner's own; other operators' labels have the same shape) appear in `$this.alr`, `alarms_state.json`, `csv/` and `logs/`, and in every shipped batch. | The digibuild side must account for this (retention, access control; its pages show login tokens only — owner to confirm, [TODO T-007](../TODO.md)). | Sample rows in `alarm_snapshot.alr`; `csv/*.csv` `user` column |

## 2.3 Conventions

| # | Convention | Details | Evidence |
|---|------------|---------|----------|
| C1 | **Vista terminology in incident text.** Description lines use Vista's terms `ACTIVE`, `NORMAL`, `ACKNOWLEDGED`, `kvitteret` plus the bot's own `RESOLVED` ("our term, not Vista's", `main.py:147`); never MainManager terms. | `describe_transitions()` `main.py:828`; comment block `main.py:135-153` |
| C2 | **Description lines are prepended, newest on top**, prefixed with `dd-mm-yyyy HH:MM Alarm bot - …` (Danish date order, local server time, `dk_now_str()` `main.py:824`). Resolution lines are prepended so that RESOLVED ends on top. | `initial_description()` `main.py:861`; `prepend_description_line()` `main.py:807` |
| C3 | **Incident name** is `CTS Alarm - <alarm_object> - <alarm_text>`, truncated to 100 characters with `...`. | `incident_name()` `main.py:872` |
| C4 | **Status labels** are exactly `ACTIVE`, `ACTIVE + ACKNOWLEDGED`, `NORMAL`, `NORMAL + ACKNOWLEDGED`, `RESOLVED` (`ALARM_*` constants). Two legacy `ACKNOWLEDGED` entries remain in `alarms_state.json` from an older code version. | `main.py:149-166` |
| C5 | **Priority is TAC Vista's:** 1 = most urgent … 9 = system noise. "Threshold ≤ N" therefore selects the *most* urgent tiers. | `config.json` `_comment`; `main.py:1060-1064` |
| C6 | **Timestamps:** Vista epochs are stored as 8-digit upper-case hex in CSV (`date1_hex`) next to a `DD-MM-YYYY HH:MM:SS` human form; state files use ISO-8601 seconds (`first_seen_iso`, `resolved_iso`); logs use `%Y-%m-%d %H:%M:%S`. All local server time; no timezone recorded. | `csv_row()` `main.py:385`; `make_state_entry()` `main.py:919`; `setup_logging()` `main.py:92` |
| C7 | **Data file conventions:** `objects.csv` and `exceptions.csv` accept `,` or `;`, `#` comments and a UTF-8 BOM; CSV audit files are `;`-delimited UTF-8 with a fixed 17-column header; `;` in alarm text is replaced by `,`. | `load_objects_csv()` `main.py:257`, `load_exceptions_csv()` `main.py:283`, `CSV_HEADER` `main.py:357` |
| C8 | **Log file naming** `logs/YYYY-MM-DD.log`, one file per day, UTF-8, `[LEVEL]` in square brackets, run separated by a 70-`=` line. | `setup_logging()` `main.py:92`, `main()` `main.py:1366` |
| C9 | **Documentation:** English prose, Danish alarm texts and Vista terms quoted verbatim; arc42 structure in `docs/arc42`, ADRs in `docs/adr` (`NNNN-slug.md`, [ADR-0001](../adr/0001-record-architecture-decisions.md)), C4 in `docs/c4`, formats in `docs/reference`; Mermaid diagrams. | [docs/README.md](../README.md) |
| C10 | **Code style:** one main module plus the optional `shipper.py`, section banners (`# ----`), `__slots__` value class `Alarm`, type hints, no globals other than constants, `argparse` CLI, exit codes 0/1/2; unit tests with fakes for HTTP (`tests/`, stdlib `unittest` + `pytest`). | `main.py`, `shipper.py`, `tests/` |
